# **Devgentic: Remote ChatOps Architecture**

## **1\. Overview**

This document outlines the architectural strategies for integrating remote "ChatOps" capabilities into **Devgentic**.

Inspired by headless agents like Moltbot, this integration allows users to control their local Mac and Devgentic agents remotely via messaging platforms (Telegram, Discord, WhatsApp). However, unlike Moltbot, Devgentic leverages its native macOS foundation and **Metacognition Engine** to ensure enterprise-grade security and zero-firewall configuration.

## **2\. The "Inverted Agent" Architecture**

Traditional chat-based agents require public endpoints (Webhooks) to receive messages. Since Devgentic is a local desktop application residing behind a router and firewall, exposing local ports is a severe security risk.

To solve this, Devgentic uses an **Inverted Agent** model:

Messaging Server ![][image1] (Pulls Data) ![][image1] Devgentic (RemoteOrchestrationService) ![][image2] CognitiveAgentExecutor

Instead of waiting for the internet to push messages to the Mac, the Mac proactively reaches out to the internet to pull messages securely.

## **3\. Core Messaging Protocols**

### **A. Webhooks (Not Recommended)**

* **Mechanism:** The messaging platform (e.g., Meta) sends an HTTP POST request to a public URL whenever a message is sent.  
* **The Moltbot Approach:** Requires a cloud server or a local tunnel (like Ngrok).  
* **Verdict for Devgentic:** **REJECTED.** Opening firewall ports or maintaining persistent Ngrok tunnels on a user's local workstation introduces unacceptable security vulnerabilities.

### **B. Long Polling (Highly Recommended)**

* **Mechanism:** Devgentic opens a standard HTTPS request to the messaging server (e.g., Telegram). If there are no messages, the server holds the connection open until a message arrives, instantly returning it. Devgentic then immediately opens a new request.  
* **Verdict for Devgentic:** **PRIMARY STANDARD.** It requires zero firewall configuration. It is simply an outbound HTTPS request using Swift's native URLSession.

### **C. WebSockets (Recommended for Teams)**

* **Mechanism:** A persistent, bi-directional TCP connection.  
* **Verdict for Devgentic:** **SECONDARY STANDARD.** Ideal for platforms like Discord or Slack (Socket Mode). Excellent for team-based control but slightly more complex to manage than Long Polling.

## **4\. Platform-Specific Implementations**

### **Platform 1: Telegram (The Optimal Choice)**

Telegram is the strongly recommended platform for Devgentic ChatOps due to its native support for Long Polling.

* **Protocol:** HTTPS Long Polling (getUpdates endpoint).  
* **Implementation Strategy:**  
  1. Create a TelegramListener actor within RemoteOrchestrationService.swift.  
  2. Use Swift's async/await with URLSession.shared.data(for: request) to poll the API.  
  3. Set a high timeoutIntervalForRequest (e.g., 60 seconds) on the URLSessionConfiguration.  
* **Security:** Whitelist specific Telegram chat\_ids or user\_ids. Ignore all other inputs.

### **Platform 2: Discord (The Team Choice)**

Discord is recommended if Devgentic is acting as a shared build server or team utility.

* **Protocol:** WebSockets (Discord Gateway API).  
* **Implementation Strategy:**  
  1. Use URLSessionWebSocketTask natively in Swift.  
  2. Implement the Gateway handshake (Opcode 10 Hello, Opcode 2 Identify).  
  3. Maintain the connection via a Heartbeat timer (Opcode 1).  
* **Security:** Restrict the bot to specific private channels or check the author.id in the message payload.

### **Platform 3: WhatsApp (The Complex Choice)**

Meta’s official WhatsApp Cloud API **forces** the use of Webhooks, making it hostile to local desktop apps. To support WhatsApp, Devgentic must use one of two workarounds:

* **Approach A: The Cloud Relay (Recommended for WA)**  
  * Deploy a tiny, free serverless function (e.g., Vercel, Cloudflare Worker).  
  * Meta sends the Webhook to the Cloudflare Worker.  
  * The Worker pushes the message to a lightweight queue (e.g., Upstash Redis).  
  * Devgentic uses Long Polling to check the Redis queue.  
  * *Benefit:* 100% secure, uses official APIs, keeps the Mac hidden.  
* **Approach B: Unofficial Web Bridge (High Risk)**  
  * Bundle a lightweight headless browser or Node.js runtime (whatsapp-web.js) within the Devgentic App bundle.  
  * The user scans a QR code generated by Devgentic to link the app as a "Companion Device".  
  * *Benefit:* No cloud servers needed.  
  * *Risk:* Meta actively bans accounts using unofficial scrapers. Not recommended for enterprise users.

## **5\. Security Model (The Metacognition Guard)**

The biggest risk of ChatOps is a compromised chat account gaining root access to the Mac. Devgentic mitigates this by injecting the source context into the CognitiveAgentExecutor.

**Integration Steps:**

1. Update AgentInput to include a source: MessageSource enum (e.g., .localUI, .telegram, .discord).  
2. Update the MetacognitionEngine.swift prompt to apply stricter rules based on the source.

**Example Metacognition Prompt Injection:**

\[SECURITY CONTEXT\]  
Source: Remote (Telegram)  
Policy:   
\- Safe (Read-only) commands are allowed (e.g., status, read logs, git pull).  
\- Dangerous commands (e.g., rm \-rf, system shutdown, uninstall) MUST be classified with a riskScore of 1.0 and Strategy REFUSE.

If a hacker compromises the user's Telegram and sends "format disk", the Metacognition Engine will intercept it, refuse execution, and the Worker agent will never load.

## **6\. MCP Extensibility via Chat**

Because ChatOps feeds directly into the BackendOrchestrationService, remote messages inherit all MCP (Model Context Protocol) capabilities automatically.

**Workflow Example:**

1. **User on Telegram:** *"Did the Vercel build fail?"*  
2. **Devgentic (Mac):** Receives via Long Poll.  
3. **AgentConnect:** Routes to ReActAgentExecutor.  
4. **MCP Tools:** Agent uses the installed mcp-vercel and mcp-github servers locally.  
5. **Response:** Agent streams the result back to RemoteOrchestrationService, which posts it to Telegram.
